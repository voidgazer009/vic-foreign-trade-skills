# Vic Skills 审核机制 v1.2（2026-11-13）

每个 Skill 每次发布前，必须按顺序通过 7 道关卡（G1–G7）。全部通过才自动推送 GitHub；任何一关不过就修，最多修 3 轮，仍不过就不推送，并向 Vic 说明原因。Vic 已授权（2026-11-12）：通过审核的 Skill 无需再问，自动上传到他的 4 个 Skills 仓库。

## G1 结构规范（自动）
`python3 tools/audit.py <skill目录>` 必须 100% 通过。内容包括：官方 skills-ref 校验；frontmatter 只使用规范字段；name 与文件夹同名；description 40–1024 字符，并写明 Use when 和中文触发词；SKILL.md 少于 500 行；包含 Workflow、Example、Gotchas、Edge cases；scripts/references/assets 中每个文件都被 SKILL.md 引用，引用的文件都存在；脚本只用 Python 标准库并支持 `--help`；不出现特定厂商的工具名；没有 TODO 或 __pycache__；evals/files 中每个测试文件都被 evals.json 或 checks.json 使用（v1.2）。

## G2 脚本回归（自动）
`evals/checks.json` 中的每条检查都要通过（G1 会自动调用 `tools/check_scripts.py`）。每修一个 bug，就加一条检查来锁定，防止复发。

## G3 隐私与真实性（自动 + 人工）
- 自动：SKILL.md、references、assets 和 evals/（含测试文件与 checks.json）中不得出现真实邮箱或电话，只能使用 example 域名、.example 后缀和 `{占位符}`（evals 自 v1.2 起纳入）。
- 人工：示例中不得编造发件人的公司、姓名、地址或资质；测试中找到的第三方公司不写进 Skill。

## G4 事实时效（自动 + 人工）
- 关税、费率、法规、平台规则这类会过期的数字，必须写明官方来源和 "Last verified YYYY-MM-DD"。超过 90 天，G1 判为不通过，需要重新核实。一个文件里有多个 "Last verified" 日期时，每一个都要检查（v1.2）。
- 发布前用 web_fetch 打开原始页面核对一遍，不能只看搜索摘要。

## G5 真实执行测试（子代理）
派测试代理，只给它 Skill 文件夹和 2–3 条 should_trigger=true 的用例（每轮轮换，并覆盖不同国家和渠道）。要求它只按 SKILL.md 完成真实任务（可联网），并报告卡住、绕路或出错的地方。
- 结果分级：Critical（会让用户亏钱、违法或出错）/ Major（流程走不通或结果明显变差）/ Minor。
- 发布条件：0 Critical、0 Major。Minor 写进 report 的待办。
- 独立性（v1.2）：G5 和 G6 应由两个独立子代理完成。某轮运行环境没有子代理工具时，由主代理按同样规则执行，并在 report 中标注"in-house（非独立）"。这样的轮次可以发布，但它的 G5 结果和 G6 分数不计入毕业标准第 2、3 条，需在之后有子代理的轮次补做独立测试和评审。

## G6 独立专家评审（另一个子代理，不看测试结果）
评审代理扮演该领域的资深从业者（例如 15 年外贸业务经理），按下表各打 0–10 分，并对每个低于 8 分的项给出具体修改建议：
1. 正确性：事实、法规、计算没有错误
2. 专业深度：一线人员才知道的经验，而非泛泛之谈
3. 可执行性：新手照着做就能得到结果
4. 安全合规：反诈骗、隐私、各国法律
5. 触发准确：该触发时触发，不该触发时不触发
6. 简洁：没有多余内容，细节放在 references
- 发布条件：平均分不低于 8.5，且没有任何一项低于 7。

## G7 发布卫生（自动）
重新打包 `dist/<name>.zip`（zip 顶层为 `<name>/`）；写 `reports/<name>-<version>.md`（G1–G6 的结果）；CHANGELOG、README 版本表、ROADMAP 状态与实际一致；semver 版本号（修复用 patch，新增能力用 minor，重构用 major）；使用 voidgazer009 noreply 身份提交；`git push`、打 tag `<name>-v<version>`；最后用 GitHub API 确认文件已上线。

## 毕业（达标后才开始写下一个 Skill）
1. 发布后至少迭代 2 轮，跨越至少 2 个不同日期。
2. 每条 should_trigger=true 的用例都至少经过一次 G5 真实执行测试并通过。
3. 最近一轮 G5 没有 Critical 或 Major；G6 平均分不低于 9.0。
4. 同类对比：搜索 GitHub、skills.sh、agentskills 等平台上的同主题 Skill，把至少 5 个和本 Skill 逐项对比（覆盖面、脚本、专业深度、安全）。只有本 Skill 在多数项上领先时才算"超过 90% 同类"，对比结果写入 report。
5. 毕业后移入 STATE.md 的 Done 列表，按轮换规则（外贸 → 物流 → 一人公司 → 自媒体）开始下一个 Skill。之后每周仍做一次轻量维护：重新核实过期的事实，处理 GitHub issues。

## 审核机制自身的迭代（每轮都做）
审核机制本身也要每天变好，目标是让问题尽量在自动关卡（G1–G4）被拦下，而不是等到 G5、G6 或 Vic 发现。
1. **漏网复盘**：每轮结束时，把 G5、G6 或 Vic 发现的每个问题逐条问一句：G1–G4 能否自动检查出来？能的话，就在 `tools/audit.py` 加一条通用规则（适用于所有 Skill）；或者在该 Skill 的 `evals/checks.json` 加一条专项检查。
2. **误报处理**：如果某条规则误伤了正确内容，就修正规则（例如加白名单或收紧匹配），并加一条反例检查，防止再次误报。
3. **评审维度**：G6 专家连续两轮都指出同一类问题时，把它加进 6 项评分细则，或单独设为必查项。
4. **只紧不松**：自动迭代只能新增规则或提高门槛。删除规则、降低分数线、放宽毕业标准，必须先问 Vic。
5. **留痕**：每次改动审核机制，都要把本文件的版本号加 0.1（如 v1.0 → v1.1），在下方变更记录写一行（日期、改了什么、因为哪个漏网问题），同步到各仓库的 `docs/review-process.md` 和 `tools/`，并在当天简报里告诉 Vic。
6. **每周体检（每周一）**：统计过去 7 天的数据：自动关卡拦下的问题数、漏到 G5/G6 的问题数、误报数。漏网率连续两周不下降时，在简报里提出改进方案。
